Spatial data = ordinary data + geometry

Most data frames have rows and columns.

Spatial data frames also record where each row lives.

ordinary variable spatial variable
population county boundary
restaurant rating restaurant location
traffic volume road segment
temperature weather station location

Note

A spatial object is usually ordinary data plus a special geometry component.

Two ways to represent space

Vector data = objects

  • point: one location
  • line: a path or route
  • polygon: an area or boundary

One row = one object.

Examples: stores, roads, counties.

In R: sf.

Raster data = grid

  • space is divided into equal-sized cells
  • each cell stores a value

One value per cell, like pixels in a photo.

Examples: elevation, temperature, satellite imagery.

In R: terra (or stars).

Note

Rule of thumb: discrete things → vector. Quantities that vary continuously over space → raster.

What is inside an sf object?

Three ingredients:

  1. ordinary columns such as NAME, BIR74, SID74
  2. one special geometry column storing the shapes (it is “sticky”: select() keeps it)
  3. metadata describing the coordinate reference system, or CRS
class(nc)
[1] "sf"         "data.frame"
st_geometry_type(nc)[1:3]
[1] MULTIPOLYGON MULTIPOLYGON MULTIPOLYGON
18 Levels: GEOMETRY POINT LINESTRING POLYGON MULTIPOINT ... TRIANGLE

You generally leave geometry alone and work with it through st_*() functions: st_area(), st_buffer(), st_join(), …

First map: geom_sf()

ggplot(nc) +
  geom_sf() +
  labs(title = "North Carolina counties")

geom_sf() knows how to draw the geometry column, so we do not write aes(x = ..., y = ...).

Mapping an attribute

nc |>
  mutate(sids_rate = 1000 * SID74 / BIR74) |>
  ggplot() +
  geom_sf(aes(fill = sids_rate), color = "white") +
  scale_fill_viridis_c() +
  labs(
    title = "Sudden infant death syndrome (SIDS), 1974–78",
    fill = "deaths per\n1,000 births"
  )

For a polygon map, aes(fill = variable) creates a choropleth.

Tip

Map rates, not raw counts: bigger counties produce bigger counts. And beware: counties with few births have noisy rates, so the most extreme colors are often the smallest counties.

Coordinate reference systems

A CRS tells R what the coordinates mean.

st_crs(nc)$input
[1] "NAD27"
st_is_longlat(nc)
[1] TRUE

Two broad cases:

  • longitude / latitude: angles on a round Earth, in degrees
  • projected coordinates: the Earth flattened onto a plane, measured in meters or feet

Warning

sf always reads coordinates as (x, y) = (longitude, latitude). The pair (36, -79) read that way is in Antarctica, not Durham!

From longitude/latitude columns to sf

places <- tibble(
  place = c("Duke", "UNC", "NC State"),
  lon = c(-78.9382, -79.0469, -78.6821),
  lat = c(36.0014, 35.9049, 35.7847)
)

places_sf <- places |>
  st_as_sf(coords = c("lon", "lat"), crs = 4326)

crs = 4326 is the code for plain GPS longitude/latitude (WGS 84), which is what most web and phone data use. Once converted, spatial layers stack like ordinary ggplot2 layers:

ggplot(nc) +
  geom_sf(fill = "gray95", color = "white") +
  geom_sf(data = places_sf, size = 4)

The most common CRS mistake

Warning

Do not treat longitude/latitude degrees as ordinary distances. One degree of longitude is about 56 miles in Durham, but 0 miles at the North Pole.

For distances, areas, and buffers, transform to a suitable projected CRS first:

nc_projected <- nc |>
  st_transform(2264) # NAD83 / North Carolina, units = US feet
Function Meaning
st_set_crs() label coordinates that are already in a CRS (numbers unchanged)
st_transform() convert coordinates to another CRS (numbers change)

Wrangling spatial data with dplyr

Most dplyr verbs work on sf objects, and the geometry comes along for the ride.

nc_west <- nc |>
  filter(NAME %in% c("Buncombe", "Watauga", "Ashe", "Avery", "Mitchell")) |>
  mutate(region = "mountains") |>
  select(NAME, region, BIR74, SID74)

When geometry is irrelevant, drop it explicitly (it makes tables smaller and code faster):

nc |>
  st_drop_geometry() |>
  select(NAME, BIR74, SID74) |>
  slice(1:5)

3       Surry  3188     5

Spatial data are still data; use ordinary data tools when appropriate.

Deriving spatial variables

Geometry can generate new variables: area, length, distance, centroid, …

nc_features <- nc_projected |>
  mutate(area_sq_miles = as.numeric(st_area(geometry)) / 5280^2)

nc_features |>
  st_drop_geometry() |>
  select(NAME, area_sq_miles) |>
  arrange(desc(area_sq_miles)) |>
  slice(1:5)

2  Robeson      941.8115

st_area() returns square feet here because EPSG 2264 is in feet; dividing by 5280² converts to square miles.

Spatial predicates

A spatial predicate asks a TRUE/FALSE geometry question.

Predicate Question
st_intersects() Do these geometries overlap or touch?
st_within() Is A inside B?
st_contains() Does A contain B?
st_touches() Do their boundaries touch (without overlapping)?
st_is_within_distance() Are they close enough?

These functions turn geometry into relationships between rows.

Spatial joins

An ordinary join matches rows using a key column. A spatial join matches rows using a spatial predicate.

places_for_join <- places_sf |>
  st_transform(st_crs(nc)) # both layers must share a CRS

places_with_county <- st_join(
  places_for_join,
  nc |> select(NAME),
  join = st_within
)

Spatial summaries and dissolving boundaries

Which counties intersect any campus buffer? Then, group_by() + summarize() merges the shapes within each group.

  • Plots
  • Code
nc_near <- nc_projected |>
  mutate(near_campus = lengths(st_intersects(geometry, st_union(buffers))) > 0)

nc_dissolved <- nc_near |>
  group_by(near_campus) |>
  summarize(n_counties = n())

p1 <- ggplot(nc_near) + geom_sf(aes(fill = near_campus), color = "white") +
  labs(title = "100 counties")
p2 <- ggplot(nc_dissolved) + geom_sf(aes(fill = near_campus), color = "white") +
  labs(title = "2 dissolved regions")
p1 + p2 + plot_layout(guides = "collect")

A spatial debugging checklist

Spatial bugs are usually data representation bugs, not syntax bugs. When something fails or looks strange:

  1. Are both objects sf objects?
  2. Do they have the same CRS?
  3. Am I measuring distance or area in a projected CRS?
  4. Are the geometries valid?
  5. Did a spatial join create one-to-many matches?
  6. Am I mapping a count when I need a rate?
st_crs(x)            # what coordinate system?
st_geometry_type(x)  # points, lines, polygons?
st_is_valid(x)       # any broken shapes?
st_bbox(x)           # does the extent look like the right place?
ggplot(x) + geom_sf()  # always look at it!

A beautiful map can still encode a poor analysis.

Part 2: Raster data with terra

A raster is a grid of values

Here is a toy raster: every cell gets one value. Most raster operations transform every cell at once.

  • Plot
  • Code
raster_grid <- crossing(
  x = seq(0, 1, length.out = 35),
  y = seq(0, 1, length.out = 35)
) |>
  mutate(value = sin(5 * x) + cos(6 * y))

p_toy <- ggplot(raster_grid, aes(x, y, fill = value)) +
  geom_raster() + coord_equal() + labs(title = "A toy raster")

p_thresh <- raster_grid |>
  mutate(high = value > 0.75) |>
  ggplot(aes(x, y, fill = high)) +
  geom_raster() + coord_equal() + labs(title = "value > 0.75")

Resolution is a choice: scale matters

aggregate() merges blocks of cells into bigger cells (here, 5 × 5 blocks, averaged).

elev_coarse <- aggregate(elev, fact = 5, fun = "mean", na.rm = TRUE)
res(elev)
[1] 0.008333333 0.008333333
res(elev_coarse)
[1] 0.04166667 0.04166667

Coarser cells hide local extremes. The scale you analyze at can change your answer.

Vector meets raster

A classic question: what is the average raster value inside each polygon?

  • Plot
  • Code
lux <- st_read(system.file("ex/lux.shp", package = "terra"), quiet = TRUE)

lux_elev <- terra::extract(elev, vect(lux), fun = mean, na.rm = TRUE)

lux |>
  mutate(mean_elev = lux_elev$elevation) |>
  ggplot() +
  geom_sf(aes(fill = mean_elev), color = "white") +
  scale_fill_viridis_c() +
  labs(title = "Average elevation by canton", fill = "meters")

sf handles the polygons, terra handles the grid, and vect() passes shapes between them. (Both layers must share a CRS; check first!)

Part 3: Spatial correlation

Why statisticians care about space

Intro statistics usually assumes observations are independent. Spatial data often aren’t:

Observations close together in space tend to be more alike than observations far apart.

  • Nearby houses have similar prices.
  • Nearby temperatures are similar.
  • Nearby counties have similar disease rates.

This is sometimes called Tobler’s first law of geography. It means location carries statistical information, and nearby observations partly repeat each other.

Simulation: what does spatial structure look like?

Left: values have nothing to do with location. Right: values depend smoothly on location, plus a little noise.

Spatial autocorrelation

Spatial autocorrelation = values at nearby locations are related to one another.

Positive (most common)

  • high near high, low near low
  • smooth patches

Negative (rarer)

  • high near low
  • checkerboard-like patterns

A useful mental model: each location asks its nearest neighbor, “are you like me?”

Let’s make that question into a number.

“Are you like your neighbor?”

For each point, find its nearest neighbor (with sf!) and record the neighbor’s value. Then compute an ordinary correlation.

add_neighbor <- function(df, label) {
  nn <- st_nearest_feature(st_as_sf(df, coords = c("x", "y")))  # index of nearest other point
  df |> 
    mutate(neighbor_value = value[nn], data = label)
}

nn_pairs <- bind_rows(add_neighbor(simulation1, "no structure"),
                      add_neighbor(simulation2, "smooth"))

nn_pairs |>
  group_by(data) |>
  summarize(r = cor(value, neighbor_value))
