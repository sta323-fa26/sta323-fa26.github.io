Lab 6: earthquakes

Due Monday November 16 5:00pm

By the end of the lab, you will

  • Query a global earthquake archive with SQL before collecting a regional subset.
  • Use projected coordinates, spatial predicates, distances, and spatial joins.
  • Construct and interpret a permutation reference distribution.
  • Compare reproducible sequential and parallel computations and assess sensitivity to spatial and temporal thresholds.

Overview

In Lab 2, you turned nested earthquake records into a rectangular data set. Now we will query a larger, frozen USGS archive to investigate two scientific questions:

  1. Across 2010–2024, do nearby earthquakes occur close together in time more often than expected if times were exchangeable among locations within each calendar year?
  2. How sensitive is that conclusion to the distances and time intervals we use to define “close”?

We will use SQL to select and summarize records, sf to identify spatial relationships, and parallel simulation to construct a reference distribution.

Data and setup

The supplied archive contains 397,964 unique earthquakes worldwide, with magnitude at least 2.5, from January 1, 2010 through December 31, 2024 (UTC). It was compiled from cached USGS downloads retrieved on October 23, 2026. Five source records with magnitudes below 2.5 were excluded from the main table and retained in an audit table. Detection varies across regions and years; this is not a complete worldwide census of all earthquakes of magnitude 2.5.

Download earthquakes.duckdb file from Duke box link and save it as data/earthquakes.duckdb in your team’s project. Download it once per working environment; do not track the file with git nor add it to GitHub.

The database is about 58 MiB. Commit your analysis and download instructions, but keep the database out of your team’s Git history. Your report should use the local file and should not download it again on every render.

The main table is earthquakes. The variables needed here are:

Variable Meaning
id Unique earthquake identifier
time_utc Event timestamp in UTC
time_s Event time, in seconds since January 1, 1970, UTC
longitude, latitude Epicenter coordinates, in degrees
mag Reported magnitude
depth Reported depth, in kilometers
place Location description
type Event type

The study region is the rectangle from 125°W to 114°W and 32°N to 42°N. Retain offshore events inside this rectangle. Use magnitude 2.5 or greater and type = 'earthquake' throughout. Use the entire observation period: January 1, 2010 inclusive through January 1, 2025 exclusive, in UTC. Organize the regional events into 15 annual catalogs. Only compare pairs of events in the same UTC calendar year, and shuffle times within years. This allows activity and geographic patterns to differ between years.

The primary statistic pools qualifying pairs across all 15 years. We do not select a year based on its earthquake count or its p-value. Our boundary rule excludes pairs spanning December 31, even if they are less than 24 hours apart; state this restriction when describing the population of pairs studied.

Use DBI, duckdb, sf, tidyverse, future, and furrr. Connect directly to the existing archive; do not import a CSV or load the full archive into R:

library(DBI)
library(duckdb)
library(sf)
library(tidyverse)
library(future)
library(furrr)

stopifnot(file.exists("data/earthquakes.duckdb"))
con <- dbConnect(
  duckdb(),
  dbdir = "data/earthquakes.duckdb",
  read_only = TRUE
)
dbExecute(con, "SET TimeZone = 'UTC'")
dbListTables(con)

Use SQL through dbGetQuery() or dbExecute() for tasks explicitly labeled SQL. Do not collect the entire catalog into R and then perform those tasks with dplyr. Use ordinary R tables for the repeated simulations.

The archive also includes archive_metadata (definition and build details), download_manifest (source chunks and checksums), excluded_events (audited exclusions), and candidate_windows (monthly counts in the study box). Your connection protects these permanent tables. DuckDB still permits temporary tables on this read-only connection; these disappear when it closes. Use temporary tables for all intermediate work.

Exercise 1 — Define and inspect the study catalog

Goal: Establish exactly which events the analysis describes.

(a) Check the source table

Inspect archive_metadata with SQL and report the archive’s observation interval, magnitude threshold, and number of excluded source records. Check download_manifest for the number of chunks and retrieval-date range. Explain why the observation period differs from the retrieval dates.

For earthquakes, use SQL to report the number of rows, number of distinct IDs, and number of rows with missing IDs, times, coordinates, or magnitudes. Check whether IDs are unique. Stop and investigate duplicate IDs rather than silently keeping an arbitrary record.

(b) Compare global and regional activity with SQL

Create a temporary table annual_activity with one row per UTC year. Report:

  • The global number of events.
  • The number inside the study box, using conditional aggregation.
  • The regional share of the global count.
  • The number of possible within-year regional pairs, n * (n - 1) / 2.

Hint: use EXTRACT(YEAR FROM time_utc) for the year and COUNT(*) FILTER (WHERE ...) for conditional counts. Cast to DOUBLE when calculating proportions if needed. Do not collect the global event records.

Compare the sum of the annual possible-pair counts with the number of pairs from treating the entire regional catalog as one group. Explain how grouping by year changes both the scientific comparison and the computational workload. A larger regional share need not indicate a change in physical earthquake risk: recording practices and global activity can also vary.

(c) Build and describe the annual study catalogs

Use CREATE TEMP TABLE study_events AS ... to select the study region, observation period, magnitude threshold, and event type in DuckDB. Exclude records missing an ID, time, coordinate, or magnitude. Keep id, time_utc, time_s, longitude, latitude, mag, depth, and an integer year. Missing depths do not require exclusion because this analysis uses epicenters. Check that you retain 24,896 events and that counts by year agree with annual_activity.

Use SQL to report each year’s event count, first and last event times, and magnitude range. Then construct a monthly summary with each month’s count, its share of its year’s total, and its rank by count within that year. Use a common table expression (a WITH clause) to calculate monthly counts, then use window functions such as:

SUM(n_events) OVER (PARTITION BY year)
DENSE_RANK() OVER (PARTITION BY year ORDER BY n_events DESC)

Include zero-event months if any occur; a calendar table built with generate_series() and a LEFT JOIN is one approach. Check that there are 180 months and that their counts sum to the regional event count. Plot the monthly counts and identify the highest-count month(s) in each year. Explain why preserving differences between annual catalogs is useful for the permutation analysis. Do not select or discard years based on these summaries.

All dates must be UTC. Keep fractional seconds for time differences. Explain which aggregations and filters happened in DuckDB before collection into R.

(d) Map the catalog

Collect only the filtered study_events, ordered by year, id, into events. Add event_index = row_number() and preserve this order for the rest of the lab. Convert longitude and latitude to an sf object using CRS 4326, then transform it to EPSG:3310 for regional distance calculations in meters. Call the projected object events_sf.

Construct a grid of 100 km squares covering the projected event locations. The grid provides a spatial summary without an additional basemap download:

grid_geometry <- st_make_grid(events_sf, cellsize = 100000)
study_grid <- st_sf(
  cell_id = seq_along(grid_geometry),
  geometry = grid_geometry
)

Use st_join() with st_intersects to attach cell_id to each event. Keep every event. If an event on a grid boundary matches multiple cells, keep the smallest cell_id for that event. Check that each event is represented once and that none has a missing cell ID. Count events per cell and map the counts, including zero-event cells. Overlay the earthquakes with magnitude represented by point size.

Do this join in a separate object: preserve the original row order of events and events_sf for pair construction. The grid summarizes locations; it does not change which events are in the study catalog. Identify one visible pattern, then explain why a spatial map alone cannot answer whether locations and times are associated.

Exercise 2 — Turn spatial proximity into a relational table

Goal: Build the reusable spatial relationships and calculate observed space–time clustering.

(a) Find nearby events

Split the row indices of events by year. For each annual catalog, use st_is_within_distance() to find events within 100 km, the largest distance needed later. Build neighbors separately by year rather than constructing all cross-year spatial pairs and discarding them afterward.

year_indices <- split(events$event_index, events$year)
idx <- year_indices[[1]]
near <- st_is_within_distance(
  events_sf[idx, ], events_sf[idx, ], dist = 100000
)

The sparse list uses positions within this year’s subset. Convert each local pair back to the global row indices with idx[local_i] and idx[local_j]. Combine the annual results into a table pairs with columns year, i, and j. Keep only i < j. Explain how this removes self-pairs and duplicate unordered pairs. Check that pair keys are unique and that events$year[i], events$year[j], and the pair’s year agree.

(b) Calculate pair distances

Add the distance between each retained pair in kilometers. Calculate only the listed distances, rather than creating a full distance matrix:

pair_distances <- st_distance(
  events_sf[pairs$i, ],
  events_sf[pairs$j, ],
  by_element = TRUE
)

pairs$distance_km <- as.numeric(pair_distances) / 1000

Report pair counts by year and in total; compare them with the possible-pair counts from Exercise 1. Explain why the latter grow quickly as catalogs grow. If no pairs remain, check your filtering, CRS, and units before proceeding. For a large annual table, calculate distances in blocks (for example 50,000 pairs at a time), using by_element = TRUE in each block. Do not construct a full distance matrix or millions of duplicated geometries at once.

(c) Join event times onto the pair table using SQL

Write the nonspatial tables pairs and events to DuckDB as temporary nearby_pairs and event_lookup tables. For example:

dbWriteTable(con, "nearby_pairs", pairs, temporary = TRUE)
dbWriteTable(con, "event_lookup", events, temporary = TRUE)

If rerunning this chunk, use overwrite = TRUE as well as temporary = TRUE. Join nearby_pairs to event_lookup twice: once to look up the time at i, and once to look up the time at j.

Use aliases to distinguish the two copies of the event table:

FROM nearby_pairs AS p
JOIN event_lookup AS a ON p.i = a.event_index
JOIN event_lookup AS b ON p.j = b.event_index

Calculate each pair’s absolute time difference in hours. Use SQL to report:

  • Each year’s number of pairs within 50 km.
  • Each year’s number also within 24 hours, and their proportion.
  • Each year’s share of the total qualifying count.

Use a LEFT JOIN to annual_activity so years with no qualifying pairs still appear. Use NULLIF() to avoid division by zero. Retain zero counts; report proportions with a zero denominator as undefined. Which years contribute most? Explain why a year with many events or spatial pairs may contribute more.

Sum the annual qualifying counts to obtain the pooled statistic T_obs. This is a count of pairs, not an equally weighted average of annual effects. For this primary analysis,

\[ T = \sum_{y=2010}^{2024} \sum_{i<j:\,Y_i=Y_j=y} \mathbf{1}\{d_{ij} \leq 50\text{ km}\} \mathbf{1}\{|t_i-t_j| \leq 24\text{ hours}\}. \]

Here, Y_i is event i’s UTC year. An indicator is 1 when its condition is true and 0 otherwise.

(d) Inspect the result

Display five qualifying pairs with IDs, magnitudes, distances, and time differences, ordered by time difference and then IDs. If fewer than five qualify, display all of them.

Explain why T_obs alone does not tell us whether there is unusually strong space–time clustering. Also explain why a single event may contribute to more than one pair without those rows being accidental duplicates.

Exercise 3 — Construct a permutation reference distribution

Goal: Answer the primary scientific question using simulation.

Our reference model is that observed times are exchangeable among event locations within each year. Keep locations and annual membership fixed. In each permutation, independently shuffle each year’s entire observed time vector without replacement, then sum qualifying pair counts across years. This preserves every year’s spatial pattern, event count, and complete set of event times (including seasonal variation and temporal bursts), while breaking the within-year association of times with locations. It does not assume uniform geographic occurrence or a constant earthquake rate.

(a) Write and check the statistic function

Write a function with this interface:

count_close <- function(times, pairs, radius_km = 50, window_h = 24) {
  # Select pairs within radius_km.
  # Look up their two times using the i and j indices.
  # Count pairs whose absolute time difference is <= window_h * 3600.
}

The vector times must follow the fixed row order in events. The function returns one number and returns zero if no pairs qualify. Verify that using the actual event times reproduces T_obs from SQL.

As a small check, use times c(0, 3600, 172800) and three pairs (1, 2), (1, 3), (2, 3), all 10 km apart. For a 24-hour window the count should be 1. Explain the result.

(b) Perform one permutation

Write shuffle_within_year(times, year_indices). Copy times, then replace each annual slice with a permutation of that slice. Use sample.int(length(idx)) to permute positions, including for a one-event year. Set a seed in the caller, perform one stratified shuffle, and pass it to count_close().

Check that each year’s sorted time vector is unchanged after shuffling. Explain why shuffling across years or shuffling the two time columns of the pair table separately would implement a different reference model. Explain why the spatial pairs and distances do not need to be recalculated.

(c) Build a reusable batch function

Write permute_batch(n_perm, times, pairs, year_indices) that returns a vector containing n_perm permuted values of the statistic. Use a readable for loop, a preallocated numeric vector, and one call to shuffle_within_year() per permutation. Do not set a seed inside the loop or the batch function; the caller will manage reproducible randomness.

For the primary analysis, prepare the indices of pairs within 50 km once outside the permutation loop. Avoid repeatedly filtering a large pair table. Keep the complete time vector, including events without any nearby pairs.

Use 999 permutations, divided into 20 batches. The following creates the batch sizes and gives each batch a reproducible random-number stream:

B <- 999L
batch_sizes <- rep(B %/% 20L, 20L)
batch_sizes[seq_len(B %% 20L)] <-
  batch_sizes[seq_len(B %% 20L)] + 1L

times <- events$time_s

plan(sequential)
serial_batches <- future_map(
  batch_sizes,
  function(n_perm) {
    permute_batch(n_perm, times, pairs, year_indices)
  },
  .options = furrr_options(seed = 323)
)
null_counts <- unlist(serial_batches, use.names = FALSE)

(d) Answer the primary question

Plot the permutation distribution and mark T_obs with a vertical line. Calculate the one-sided Monte Carlo p-value:

\[ p = \frac{1 + \#\{T_b \geq T_{\mathrm{obs}}\}}{B+1}. \]

Also report the observed count, mean permutation count, and their ratio. If the mean permutation count is zero, report the ratio as undefined and report the two counts directly. With 999 permutations, the smallest possible reported p-value is 0.001; do not report a p-value of zero.

Write a short answer to scientific question 1. State what was randomized, what was held fixed, and whether the observed count is unusually large under this reference model. Do not use a binomial test on the pair indicators: different pairs can share earthquakes.

Exercise 4 — Scale the computation and check the spatial scale

Goal: Evaluate parallel computing and answer the second scientific question without rebuilding the expensive spatial relationships.

(a) Compare sequential and parallel execution

Time the same 20-batch calculation using plan(sequential) and plan(multisession, workers = 2). Keep the data, batch sizes, function, permutation count, and furrr_options(seed = 323) identical.

Use elapsed time, for example system.time(...)[["elapsed"]]. For each plan, run the workload once as a warm-up, then time three repetitions and report the median elapsed time. These timings measure an already-started worker session; say explicitly that worker startup is excluded. Do not include database queries, mapping, or pair-table construction in these times.

Check that the sequential and parallel vectors agree using all.equal(). Report speedup as sequential median time divided by parallel median time. You receive full credit for a correct parallel implementation even if it is slower. Explain the result in terms of task size, worker overhead, and data transfer. Do not add artificial delays to create a speedup.

Only ordinary vectors and tables should enter the workers. Do not pass con or perform concurrent database writes.

(b) Investigate the definition of “close”

Repeat the analysis for all six prespecified combinations:

Spatial distance Time windows
25 km 6 hours, 24 hours
50 km 6 hours, 24 hours
100 km 6 hours, 24 hours

Extend your batch function to return the statistic for all six combinations. Within each permutation, shuffle times once within every year, then evaluate all six combinations on that same complete stratified shuffle. Use the existing 100 km pair table throughout. Run the batches in parallel, with reproducible randomness.

Precompute spatial pair selections outside the loops and calculate absolute time differences once per permutation for reuse across settings. Hint: tidyr::crossing() can construct the six settings. Your outer loop can iterate over permutations and an inner loop over settings. Parallelize only the outer batches; do not create workers inside workers.

(c) Compare the scientific results

Create one compact table containing distance, time window, observed count, mean permutation count, observed-to-expected ratio, and Monte Carlo p-value. Include the number of spatial pairs available at each distance; when it is zero, label that setting uninformative.

Produce one plot comparing observed-to-expected ratios across the six settings. Answer scientific question 2 in a paragraph. Explain why larger raw counts at larger thresholds do not by themselves demonstrate stronger clustering. Treat these six results as a sensitivity analysis, not six independent discoveries or an opportunity to select the smallest p-value.

(d) Conclude and clean up

Write a final paragraph connecting both scientific questions. Include one limitation of the reference model: within each year, it assumes that event times can be reassigned throughout the study region. Distinct local temporal trends or changes in detection could also produce a space–time association. Explain why rejecting this null does not uniquely identify an aftershock mechanism. Discuss the exclusion of cross-year pairs and the fact that a pooled pair count gives greater influence to years with more qualifying pairs. Distinguish evidence of association from a claim that the effect is identical in every year.

Finally, explain why keeping only nearby pairs and computing geometry once may matter more for scalability than adding workers. Restore sequential execution and disconnect from DuckDB at the end of the report:

plan(sequential)
dbDisconnect(con, shutdown = TRUE)

Style guidelines

All assignments in this course must employ proper coding style, as outlined below:

  • All code should obey the 80 character limit per line (i.e. no code should run off the page when rendering or require scrolling). To enable a vertical line in the RStudio IDE that helps guide this, see the style guidelines from lab 0 or ask a member of the teaching team for help.

  • All commas should be followed by a space.

  • All binary operators should be surrounded by space. For example x + y is appropriate. x+y is not.

  • All pipes %>% or |> as well as ggplot layers + should be followed by a new line.

  • You should be consistent with stylistic choices, e.g. only use 1 of = vs <- and %>% vs |>

  • Your name should be at the top (in the YAML) of each document under “author:”

  • All code chunks should be named (with names that don’t have spaces, e.g. ex-1, ex-2 etc.)

  • File names in your GitHub repo such as lab-x.qmd must not be changed and left as provided. Additionally, your repo must pass certain basic checks. The results of these checks are visible on GitHub via the badges at the top of your README and the actions tab. These are meant to give you feedback around the structure and reproducibility of your repository and assignment - they do not assess the correctness of your work. You should consider them a necessary but not sufficient condition when turning in your work - passing all of the checks simply means your have met a minimum standard of reproducibility for the assignment.

Fundamentally, the check is making sure 1) you only have the files you should in your repository, 2) your .qmd renders.

If you have any questions about style, please ask a member of the teaching team.
